# Getting into OperatorHub

What a submission consists of, what has to be true before making one, and the two decisions in
this repository that a reviewer will ask about.

## What is submitted

A pull request to [`k8s-operatorhub/community-operators`](https://github.com/k8s-operatorhub/community-operators)
(which feeds operatorhub.io and the community catalogue on OpenShift), adding one directory:

```
operators/keydra-operator/0.0.1/
├── manifests/
│   ├── keydra-operator.clusterserviceversion.yaml
│   ├── keydras.keydra.io-v1.crd.yml
│   └── keydraconnections.keydra.io-v1.crd.yml
└── metadata/
    └── annotations.yaml
```

That is `target/bundle/keydra-operator` verbatim. It is generated by the build from the same
classes the CRDs come from, so the CSV's owned CRDs cannot disagree with the CRDs beside them —
which is one of the things the reviewer's automation checks and one of the more common reasons a
first submission fails.

```bash
./mvnw package -DskipTests
operator-sdk bundle validate ./target/bundle/keydra-operator \
  --select-optional suite=operatorframework
```

CI runs that on every push. Run it locally before opening the pull request anyway: the answer
arrives in thirty seconds here and in a day there.

## Before the first submission

**The image has to be public and multi-architecture.** `quay.io/keydrahq/keydra-operator:0.0.1`,
pushed by `.github/workflows/image.yml`, for `linux/amd64` and `linux/arm64`. The catalogue pulls
it on clusters this project has never seen; a private repository fails at install time rather than
at review time, which is worse.

**The version in the CSV has to match the tag.** `keydra-operator.v0.0.1` comes from the project
version in `pom.xml`. A release is a tag `v0.0.1`, and the two are the same number by construction
rather than by somebody remembering.

**The API group has to be one the project can defend.** `keydra.io` matches the `io.keydra` Java
package root the project already uses. Nobody verifies domain ownership, but a group somebody else
turns out to be using is a rename after the fact, and a rename of an API group is a migration for
everybody who installed it. Settle this before `v1alpha1` is in anybody's cluster, because
afterwards it is not settleable.

**`alm-examples` has to install.** OperatorHub renders the "Create instance" form from it, and it
is the first thing anybody does. The two examples in `KeydraBundle` are the minimum that works —
and they only work in a namespace that already has the Secret and the PostgreSQL, which is
mentioned in the CSV description because a form that produces a `Degraded` resource with no
explanation is worse than no form.

## The two things a reviewer will ask about

**Why `Basic Install` and not higher.** The
[capability levels](https://sdk.operatorframework.io/docs/overview/operator-capabilities/) go from
Basic Install through Seamless Upgrades, Full Lifecycle, Deep Insights and Auto Pilot. This is
honestly Basic Install today: it installs and it reports status. It is not Seamless Upgrades until
there is a second version to upgrade from and something that has done it. Claiming a level that has
never been exercised is how a catalogue entry becomes a bug report, and the level is trivially
raised in a later release once the thing it claims has happened.

**Why `MultiNamespace` is unsupported.** OLM's MultiNamespace mode hands the operator a list of
namespaces at install time. The `Keydra` controller would be fine with it. The `KeydraConnection`
controller looks up its installation in the resource's own namespace and would therefore be right,
but for a reason nobody had checked — and "it happens to work" is not the same claim as "it is
supported". `AllNamespaces`, `OwnNamespace` and `SingleNamespace` are all exercised.

## Upgrades

The channel is `alpha` and the CSV names no `replaces`. The first version in a channel cannot
replace anything; the second must, or OLM has no upgrade path and installs the new one beside the
old.

For `0.0.2`:

```java
@CSVMetadata(
        // …
        replaces = "keydra-operator.v0.0.1")
```

And the CRDs have to stay compatible. A `v1alpha1` field that changes meaning is a change to a
resource somebody has already applied, and OLM's upgrade will apply the new CRD over the old one
without asking. Adding fields is safe; narrowing a validation rule is not, because it can make an
existing resource invalid — and a resource that fails validation on an operator upgrade is a
console that stops being reconciled at the moment somebody was upgrading it.

## Red Hat's certified catalogue

Different repository (`redhat-openshift-ecosystem/certified-operators`), different requirements: a
Red Hat base image (this uses UBI 10 already), a passing Preflight scan, and a
`connect.redhat.com` project. Worth doing after the community entry exists rather than instead of
it — the community catalogue is installable on OpenShift too, and it is the one that does not need
an account.
